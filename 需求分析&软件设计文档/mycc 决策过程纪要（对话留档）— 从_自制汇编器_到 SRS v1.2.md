# mycc 决策过程纪要（对话留档）

> **这份文档是什么**：把"为什么最后是这个方案"完整记下来的过程档案。不是需求，不是设计，而是**决策链**。
> **为什么值得留**：下面的每一条结论都不是一次成型的——其中 5 条经历了推翻或改判。答辩时被问"你们为什么这么设计"，翻这份文档比翻 SRS 更快。

## 0. 一句话总结

起点是一个很窄的问题（"有没有能自定义指令集的汇编器"），输出是一份 13 章 + 4 附录的完整 SRS，覆盖**可选指令集机制**与**PySide6 图形工作台**两大功能，并附带一套可自动化执行的验收体系（`AC-01`~`AC-13`、`FM-01`~`FM-21`、三环境矩阵）。
**规模变化**：26 条固定白名单 → 可配置 profile（`PF-01`~`PF-07`）+ 能力守卫 lowering 表；无界面 → CLI + GUI 双界面；`AC` 从 8 条 → 13 条。

## 1. 阶段时间线

| 阶段 | 触发问题 | 产出与结论 |
| --- | --- | --- |
| **A** 汇编器调研 | 有没有可自定义指令集的汇编器？自己做难吗？ | 三条路线（GNU as `.insn` / 改 binutils / 表驱动 customasm）；**自制汇编器不难**（300~500 行 Python，无算法难点）；关键洞察：**"拒绝不支持的指令"比"添加自定义指令"更值钱** |
| **B** 显示链路 | 只有 VGA，能直接转 HDMI 吗？ | 不能靠线直连，需**有源**转换盒（方向不对称是常见坑）；给出四条方案排序；**顺带发现"给 FPGA 直接加 HDMI（原生 TMDS）"可行** |
| **C** C 编译可行性 | 想加上"从 C 语言子集编译"的功能？ | 分清"只想让 C 跑起来"与"自己写编译器"；确立架构决策：**编译器出** `.s` **文本，不出机器码**；列出工具链缺口表（`lui` 致命）；给出 C 子集 8 级阶梯；**强烈建议把编译器与硬件解耦**（qemu 回路） |
| **D** 编译原理澄清 | C 到汇编要经过哪几步？ | 十步流水线 + 前端/中端/后端划分；关键结论：**5~9 步可整段砍掉，1~4 与 10 绕不过去**（这直接支撑了后续"不上 IR、不上寄存器分配"的选择） |
| **E** GCC 边界 | 缺指令时 GCC 能出正确汇编吗？ | GCC 对 `-march` 是"整档选、不能做减法"；算出真实缺口（`lui` + 四个分支比较才是关键，`sll`/`xor` 几乎不出现）；给出三条路 + **objdump 助记符白名单 lint** 这一低成本关键手段 |
| **F** SRS v1.0 | 要一份需求分析文档（含评分标准） | 26 条固定白名单、8 章 + 3 附录；建立 ID 前缀体系、追溯矩阵、故障模式表 |
| **G** SRS v1.1 | 加可选指令集合 + 图形界面 | **识别出三处结构性冲突 + 一处语义隐患**（见 §3）；引入能力守卫 lowering 表；GUI 定为 Tkinter / P1 |
| **H** SRS v1.2 | 定 GUI 技术栈、定位、优先级 | GUI 改判 **PySide6**；定位收敛为 **IDE 式工作台**；优先级 **ISA P0 / GUI P1**；`CN-01` 首次放开并配防侵蚀机制 |

## 2. 五条被推翻或改判的结论（**最有价值的部分**）

### 2.1 从"先用 customasm 顶着"到"自研编译器"（阶段 A → C）

*   **A 阶段建议**：如果只是想让项目推进，先用 customasm 顶一阵，等需要 `.include`/多段/想练手再自己写。
    
*   **C 阶段改判**：用户决定自研编译器并作为软工课设。理由不再只是"练手"——**自研编译器是唯一能同时把"语言语义"与"目标 ISA 子集边界"两个约束握在手里的方案**。
    
*   **为什么这不是反复**：A 阶段的目标是"让 CPU 跑上程序"，C 阶段的目标变成"交付一个编译器"。目标变了，最优解就变了。这条值得记住：**方案的优劣依附于目标，而目标本身会演化**。
    

### 2.2 GUI 技术栈三变：Tkinter → Web UI → PySide6（阶段 G → H）

| 版本 | 选择 | 理由 | 为什么被改 |
| --- | --- | --- | --- |
| v1.1 | Tkinter | 由 `CN-01`（仅标准库）反推的唯一解 | 无语法高亮 API、行号栏与错误标记需自写、CJK 与大文件/DPI 在 Linux 上不稳定 |
| v1.2 初 | **Web UI**（用户所选） | 界面最强、WSL2 最省事、HTTP 接口天然可测 | **被复核否决**：① 浏览器沙箱下无法"另存为指定路径"，与"IDE 式工作台"定位**硬性冲突**；② 需放开 `NFR-603` 并新增回环安全面（Origin 校验、随机 token）；③ 要维护第二套前端技术栈 |
| v1.2 终 | **PySide6** | `QPlainTextEdit` + `ExtraSelection` 精确到列的诊断定位、`QFileDialog` 原生文件对话框、`QProcess` 非阻塞子进程、`QT_QPA_PLATFORM=offscreen` **提供无头可测性** | — |

**关键教训**：Web UI 不是"不好"，而是**与已选定的 GUI 功能定位不兼容**。用户先后给出的两个选择（Web UI + IDE 工作台）单独看都合理，合起来有硬冲突——**这是我在改写前专门先做对比再让用户定的原因**。

### 2.3 除法边界语义（v1.0 → v1.1/v1.2）

*   **v1.0**：`b == 0` 时 `__divsi3` 返回 `INT_MIN`（当时无硬件除法，随便定的）。
    
*   **v1.1 改判**：对齐 RISC-V 硬件语义——`b == 0` → `div` 返回 `-1`、`rem` 返回被除数；`INT_MIN / -1` → `div` 返回 `INT_MIN`、`rem` 返回 `0`。
    
*   **为什么必须改**：C 标准把这几种情形定义为**未定义行为**，不指定就真的会不一致。一旦可选指令集允许启用硬件 `div`，同一程序在启用/未启用 `EX-02` 的两个 profile 下就会**静默产生不同结果**，直接破坏 `AC-09`（跨 profile 行为不变性）。
    
*   **教训**：**"未定义行为"在单实现里可以随便定，在多配置下必须钉死。** 这是引入可选指令集带来的隐性成本。
    

### 2.4 `CN-01`（仅标准库）从不许放开到放开 + 防侵蚀

*   v1.0/v1.1：`CN-01` 是"全部仅标准库"，被引用 6 处以上。
    
*   v1.2：首次放开——`core`/`cli` 仍仅标准库，`gui` 允许且仅允许 PySide6。
    
*   **配套机制（关键）**：放宽一条贯穿全文的约束，危险的不是放宽本身，而是它在实现期被逐步掏空。故补：`CN-18`（白名单封闭）、`CN-19`（LGPLv3 履约）、`NFR-501`（精确集合断言）、`FR-812`（import 扫描）、`RS-18`（侵蚀风险）、新增 `RO-06`（环境准备者角色）、`NFR-506`/`NFR-311`/`FR-813`（离线安装与 `--doctor`）。
    
*   **教训**：**放宽约束时，必须同时给出"防止它继续扩大"的机制**，否则约束会变成一句空话。
    

### 2.5 GUI 优先级：P1（曾被考虑升 P0）

*   用户明确选择 **ISA 配置 P0、GUI P1**。
    
*   但有一处例外被单独标为 P0：**工作台的 offscreen 可测性**（`FR-919`/`FR-920`/`NFR-803`/`NFR-807`）。理由：没有它，GUI 就会变成"交付物里一大块没人验证的代码"（`RS-11`）。
    
*   **该取舍被明确标注为可逆**：若课程对"不同用户的人机界面"评分权重更高，可升为 P0，并同步改 `AC-12` 的措辞。

## 3. v1.1 改写时发现的三处结构性冲突 + 一处语义隐患

用户提出"加可选指令集 + 图形界面"时，表面是"加两个功能"，实际有四处自相矛盾：
| # | 冲突 | 原写法 | 处理 |
| --- | --- | --- | --- |
| 1 | 固定白名单 vs 可配置 | `CN-02` "严格限定为 26 条" | 改为"由 profile 派生，恒为 RV32IM 与 CPU 支持集的子集" |
| 2 | 专用开关 vs 组合表达 | `FR-109` 的 `--no-lui`/`--no-vshift` | 开关数会随可选组线性膨胀，且**无法表达"只启用 div 不启用 mul"** → 改为通用 `--enable`/`--disable`，旧开关降为兼容别名 |
| 3 | 仅标准库 vs 引入 GUI 框架 | `CN-01` | v1.1 被逼出唯一解 Tkinter；v1.2 显式放开并配防侵蚀机制 |
| 4 | 语义隐患 | 除零边界 | 见 §2.3，由 `D-11` 系统性消除 |

**方法论价值**：新增功能的需求文档评审，重点应放在**"它与既有约束是否相容"**，而不是"它本身是否合理"。这四处冲突没有一处是用户提出的功能本身有问题。

## 4. 核心机制：能力守卫的 lowering 表（`D-07`）

v1.1 引入的最重要抽象，也是让"可选指令集"成立的关键。
**形态**：每个抽象操作 → 有序的（守卫, 展开, 原因）列表，codegen 取首个守卫成立者。

```
抽象操作: `*`
  ① 守卫: mul ∈ ISA      → mul rd, a, b      原因: 硬件支持乘法器
  ② 守卫: (总是成立)      → call __mulsi3     原因: profile 不含 mul，回退运行时库
```

**四项收益**（都写成了可验证的需求）：

1.  新增硬件变体**零 Python 代码改动**，只加一个 `isa/*.json`（`NFR-405`）
    
2.  可行性可在**编译前静态判定**，错误信息质量远高于运行期才发现（`FR-114`）
    
3.  每步选择都带"为什么"，直接成为 GUI 教学面板的数据源（`FR-117`/`FR-521`/`FR-909`）
    
4.  顺手消掉了上面第 2 处冲突（开关膨胀）
    

**配套**：`MV-ISA`（9 条必须有、无回退）、`EX-01`~`EX-06`（可选组）、`PF-01`~`PF-07`（内置 profile）、`CN-16`（profile 是 ISA 事实唯一来源，四处派生不得硬编码）、`D-10`（配套的 lint profile 敏感性验证）。

## 6. 旁支结论（不在 SRS 中，但可复用）

这些是早期问答里出现的技术结论，与最终交付物无直接关系，但值得留档。

### 6.1 汇编器自研的成本分布（按痛苦程度）

1.  伪指令展开（展开后地址变，前向标签要迭代收敛）——最容易出 bug
    
2.  表达式求值 + 前向引用（`%hi`/`%lo`）
    
3.  B/J 型立即数的位散列——**一定要给每个编码函数写单元测试**
    
4.  立即数范围检查与错误信息——回报最高、最容易被偷懒
    
5.  链接/重定位——**先别做**
    

*   验证方法：与标准工具链汇编同一文件，二进制逐字节对比，能覆盖 90% 编码 bug
    

### 6.2 缺指令时喂 GCC 的实用手段

*   `-ffixed-x30 -ffixed-x31`：让 GCC 永不碰 `t5`/`t6`，从而在 `.s → .s` 后处理脚本里有**两个真正干净的临时寄存器**。这是"后处理路线"能否成立的前提
    
*   **助记符 lint 跑在** `objdump -d` **上，不是跑在** `.s` **上**——因为 `.s` 里有 `li`/`mv`/`j`/`ret`，只有 objdump 输出才反映 CPU 真正执行的东西
    
*   必加 flag：`-march` 绝不能带 `c`；`-fno-pic -fno-pie -mcmodel=medlow`；`-mstrict-align`；`-mno-relax`；`-nostdlib -ffreestanding`
    
*   **两个会咬人的坑**：① `memcpy`/`memset` 由 GCC 中端自动生成，`-fno-builtin` 挡不住，`-nostdlib` 下必须自己提供；② `sp` 初值与 `ra` 归调用方管，必须自己写 `crt0`
    

### 6.3 VGA → HDMI 的实际结论

*   不能靠线直连，需**有源**转换盒；方向不对称（HDMI→VGA 的便宜线能用，VGA→HDMI 必须有源+供电）
    
*   有些适配器从 VGA 第 9 脚偷电，而 FPGA 开发板的 VGA 座常悬空该脚 → **买带独立 USB 供电的**
    
*   兼容性坑：自写时序发生器常用 25.000 MHz，标准是 25.175 MHz（差 0.7%），少数设备锁不上
    
*   **给 FPGA 直接加 HDMI 可行**：TMDS 本质是差分串行，单端输出 + 约 50Ω 串阻可用；640×480@60 只需 25 MHz 像素时钟 → 250 MHz 位时钟，`OSERDESE2` 走 5x DDR 时序不紧张

## 9. 这套流程本身可复用的部分

> 如果之后还要写别的 SRS 或做类似的功能扩展，下面几条是本次真正起作用的方法。

1.  **背景与需求分离，且为每条需求标"来源"**：任何需求都能反查到是哪个背景/场景/角色提出的。防止"拍脑袋功能"。
    
2.  **假设必须附依据**：`AS-02`（四条指令能按时补完）的依据写的是具体的改法（`lui` 复用 U 型立即数生成器；`sll`/`srl`/`sra` 复用桶形移位器只改移位量来源），而不是"应该不难"。
    
3.  **故障模式单独成章，逐条给"检测方式 + 期望行为 + 退出码 + 用户可见信息 + 测试用例"**：这是评分标准里"故障模式及处理方式有定义"的直接得分点。
    
4.  **优先级与"使用频率"两列并列做一致性校验**：P0 必须是"每次/常见"。例外必须逐条解释（本次解释了 7 处，包括"机制是 P0 但具体可选组可裁剪"）。
    
5.  **把架构约束变成自动化检查**：`FR-809`（lint 的 profile 敏感性）、`FR-810`（core 导入图不含 GUI）、`FR-812`（依赖白名单扫描）、`FR-519`（禁止选项名特判）。这些把"我们打算这么做"变成"不做就红"。
    
6.  **用不变性属性替代穷举**：`AC-09`（跨 profile 行为不变）比"枚举所有组合"更强也更省；`NG-10` 明确拒绝穷举。
    
7.  **放宽度量约束时同步给出"防扩张机制"**（见 §2.4）。
    
8.  **在功能扩展前先做"与既有约束的相容性检查"**（见 §3）。
    
9.  **变更控制流程末尾附"本次变更的实际留档"**：记录提出→影响分析→判定→同步→基线五步的**真实执行结果**，包括发现了几处冲突。这证明流程不是摆设。
    
10.  **明确"可逆"与"不可逆"的取舍**：GUI 的 P1 定位被标注为可逆并给出升 P0 的具体改法；`CN-01` 的放开被标注为需要配套机制。
